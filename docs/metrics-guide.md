# 指标解读

Codex Latency Monitor 被动读取本机已经完成的 Codex Turn，用于区分两类体验问题：**开始输出前等待过久**，以及**开始输出后整体推进过慢**。它不会发送探针，也不会保存会话正文或工具参数。

## 先看什么

| 场景 | 优先看 | 代表什么 |
| --- | --- | --- |
| 感觉“等很久才开始回答” | TTFT p50、p95 | 从发起 Turn 到首次模型输出的等待时间 |
| 感觉“已经开始回答但推进很慢” | TPS p50、p5 | 从首次输出到 Turn 完成的有效输出速度 |
| 偶发卡顿 | TTFT p95 与 p50 的差值；TPS p5 与 p50 的差值 | 少数较差请求是否显著拉开了体验 |
| 想定位某一次异常 | 时序图与最近 50 轮表格 | 该 Turn 的准确完成时间、TTFT、TPS 与工具标记 |

## 两个基础指标

### TTFT

**TTFT（Time To First Token）** 是从 Turn 开始到首次模型输出的时间，越小越好。

它主要反映开始生成前的等待。VPN、网络链路、服务排队、请求重试或上下文处理都可能使它升高。

### TPS

**TPS（Tokens Per Second）** 是从首次模型输出到 Turn 完成期间的有效输出速度，越大越好。

它采用当前 Turn 的输出 token 数除以这段时长计算。工具调用和其他等待不会被扣除，因此它反映的是一次 Turn 的实际推进速度，而不是模型逐 token 的原始吞吐。TPS 下降可能来自模型输出、网络中断或工具等待，需结合“工具”标记与时序图判断。

## p50、p95 与 p5 是什么

分位数用于同时展示典型体验和较差体验，避免少数极端请求把均值拉偏。

| 指标 | 含义 | 用途 |
| --- | --- | --- |
| p50 | 中位数；约一半 Turn 优于它，另一半差于它 | 典型体验 |
| TTFT p95 | 约 95% Turn 的 TTFT 不高于该值 | 较慢的首包等待；TTFT 越高越差，因此看高分位 p95 |
| TPS p5 | 约 5% Turn 的 TPS 不高于该值 | 较慢的输出速度；TPS 越低越差，因此看低分位 p5 |

`p5` 不是“5 秒”，`p95` 也不是“95% 的请求失败”。它们都是同一批已完成 Turn 的位置指标。

例如：

```text
TTFT p50 6.7s · p95 15.4s
TPS  p50 61.0/s · p5 22.0/s
```

这表示典型 Turn 约 6.7 秒出现首个输出，但较慢的 5% 可接近 15.4 秒；典型有效输出速度约为每秒 61 个 token，而最慢的一小部分会降到约每秒 22 个 token。

## 为什么不以均值为主

均值可以作为补充，但不适合作为这个工具的主指标。一次网络卡顿或超长工具等待就可能把均值显著拉高或拉低，却无法看出“多数请求是否正常”以及“较差请求有多差”。

因此：

- TTFT 使用 p50 + p95，分别看典型首包和慢首包；
- TPS 使用 p50 + p5，分别看典型输出和慢输出；
- 如果 p50 稳定但 TTFT p95 升高，通常是偶发首包抖动；
- 如果 TPS p50 稳定但 TPS p5 降低，通常是少数 Turn 在输出阶段变慢。

## 界面范围

| 位置 | 数据范围 |
| --- | --- |
| SwiftBar 顶部 | 最近完成的一轮 TTFT 与 TPS |
| SwiftBar 最近 10 轮 | 最近完成的 10 个 Turn |
| SwiftBar 当日汇总 | 今天 00:00 至当前的完成 Turn；TTFT p50/p95、TPS p50/p5 |
| 本地报告汇总卡片 | 今天 00:00 至当前的完成 Turn；与 SwiftBar 当日汇总相同 |
| 本地报告时序图 | 昨天 00:00 至当前的完成 Turn |
| 本地报告表格 | 最近 50 个 Turn |

当某个 Turn 缺少 TTFT、输出 token，或无法得到有效输出阶段时长时，TPS 会显示为 `N/A`。SwiftBar 只在当天确实存在这类 Turn 时，才会在“今天”一行显示 `N/A` 数量。

## 使用边界

该工具用于观察本机实际使用体验，不能单独证明问题一定发生在 VPN、Codex 服务端或某个工具上。出现异常时，建议先用时序图定位时间点，再结合该 Turn 是否有工具标记与本机网络状态判断。
