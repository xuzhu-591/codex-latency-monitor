# Codex 与 Claude Code 本地延迟监控设计

## 1. 目标

用 SwiftBar 在 macOS 菜单栏被动展示本机日常 AI 编码请求的真实体验，不发送任何探针请求。

- 同时支持 Codex 与 Claude Code。
- 顶部展示最近完成的一轮，并标注来源与模型。
- TTFT 与 TPS 仅在按模型拆分的当天汇总中展示，用于区分“迟迟没响应”和“整轮工作很慢”。
- 下拉菜单展示最近 10 轮；本地报告展示趋势与最近 50 轮。
- 不保存消息正文、推理文本、工具参数或工作区路径。

## 2. 统一指标

一个 Turn 是一次真实用户输入引起的完整 Agent 工作，可包含思考、模型输出和工具循环。

| 指标 | 展示名 | 计算方式 | 作用 |
| --- | --- | --- | --- |
| 首个响应等待 | TTFT | 用户提交到首个助手输出 | 判断何时开始获得响应 |
| 端到端产出效率 | TPS | 输出 token 总数 ÷ 用户提交到 Turn 完成的总时长 | 判断这一轮整体是否拖慢工作 |
| 总时长 | Duration | 用户提交到完成 | 解释长 Turn |
| 工具标记 | 工具 | Turn 内是否有工具调用 | 为长耗时提供上下文 |

TPS 的分母保留 TTFT、模型思考、网络与工具等待。它刻意不使用“首 token 后 TPS”：后者可能在首包长时间等待后给出虚高数值，不能代表从提问到拿到结果的体感。

## 3. 界面

默认菜单栏文本：

```text
cx · gpt-5.6-sol
```

展开菜单：

- 最近 10 轮：完成时间、`cx` 或 `cc`、模型和工具标记；不展示 TTFT、TPS；
- 当前进行中 Turn：来源与当前模型；
- 当日汇总：按“来源 + 模型”显示轮数、TTFT p50/p95、TPS p50/p5 与 `N/A` 数量；
- 本地报告入口。

报告使用 `● cx` 与 `◆ cc` 作为来源图标。时序图的采样点、悬停提示和最近 50 轮表格都显示来源与模型，避免混淆。

## 4. 数据处理原则

| 来源 | 读取范围 | Turn 起点 | Turn 完成 | 特殊处理 |
| --- | --- | --- | --- | --- |
| Codex | `~/.codex/sessions/` | Codex 记录的开始事件 | Codex 记录的完成或中止事件 | 采用 Turn 上下文的模型，采用原生 TTFT，累计输出 token 更新 |
| Claude Code | `~/.claude/projects/` | 真实用户消息 | assistant `end_turn` | 采用最终助手消息的模型；排除 `subagents/`、工具结果、边车、元事件和压缩摘要 |

Claude Code 每个助手消息按消息 ID 采用最大的 `output_tokens` 计数，避免日志重复或更新事件造成重复累计。Claude 的 TTFT 由第一个 `thinking` 或 `text` 记录在本地重建；它用于体验观察，不声称是服务端原生首字节时间。

## 5. 非目标

- 不扣减工具等待，不估算纯模型吞吐，不生成逐 SSE token 速率；
- 不注入代理、修改 Codex/Claude 配置，或主动探测网络；
- 不上传数据，不提供账号体系、云端同步或常驻服务；
- 不将不同工具的绝对值解释为服务端性能基准。趋势比较应优先在同一来源内进行。

## 6. 验收条件

1. 最新 Turn 在菜单栏清楚显示 `cx` 或 `cc` 及模型。
2. TPS 以用户提交到完成的总时长计算，TTFT 不再从其分母扣除。
3. Codex 既有历史记录在升级后自动按新口径重新计算。
4. Claude 工具循环不会拆成多轮；工具结果、边车和子代理不会被统计为用户 Turn。
5. 报告可通过图标、表格和悬停提示区分来源与模型；当天汇总按模型分组。
6. 所有单元、集成、端到端测试通过，且 fixture 中的正文不进入报告或本地指标数据。
